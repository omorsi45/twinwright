# Claims

Every claim the project makes, with the test or CI job that proves it and where that proof runs. The table has one row per numbered goal of the project's design, one per item of its milestone plan and of its scope decisions, and one per factual claim in the README and the security notes.

How to read it.

- **Proven by** names backticked tests (for example `TestDemo`) and backticked CI jobs written as the workflow file, a slash and the job ID (for example `integration.yml/real-model`). A row that nothing proves says `not verified`. A row for scope that was dropped says `cut` and gives the reason. No row is left without one of these.
- **Where it runs** is one of: local suite (`go test ./...`), CI fast lane (`ci.yml`), Integration (`integration.yml`), opt-in (the environment variable that enables it is named), or local run (the document that records it is named). `none` means nothing runs.
- A cited test is checked to exist and a cited job is checked to exist in its workflow file, by `TestClaimsTableReferencesExist`. The same check reads the Go source of each cited test: a row that cites a test which skips unless a `TWINWRIGHT_TEST_` variable is set has to name that variable, or say Integration, in "Where it runs". It reads names, not types, so a test that reaches its skip through a method call, a callback or a branch is not seen. Every relative link in the README, the architecture page, this page and the guide is checked by `TestDocLinksResolve`, which also requires the heading a link names (`page.md#heading`) to exist in the target file. None of these checks says that a cited test is the right test for its claim, or that a cited job passed. Those are for the reader.
- The CI fast lane runs `go test ./...`, so every test marked local suite also runs there. A job in the Integration workflow runs on its triggers (a push to `main`, a pull request, or a manual dispatch); `perf` runs on manual dispatch only.
- What CI showed, as of 2026-10-29. Each of `real-model`, `observability` and `demo-stack` passed on its first Integration run on 2026-10-28 and on every Integration run since. The `docker` job, with its container tests, and `postgres` on 16 and 17 passed on every Integration run from 2026-10-28 on. `perf` is skipped on a push or a pull request and passed on its first manual dispatch on 2026-10-28 and on every manual dispatch since. It did not run in the `pull_request` runs of 2026-10-29, so the `perf` job has not run with the changes made to the `perf` command after the last of those dispatches (their tests are in the local suite).
- The `pull_request` runs of both workflows on 2026-10-29, for the branch that holds the review fixes, passed every job except `perf`. In the CI workflow: `build` (format, vet, build, test), `race`, `end-to-end` (including `make demo`), `regression-gate` (with the missing-write regression check) and `security`. In the Integration workflow: `postgres` on 16 and 17, `docker` (with the step that requires each `TestPythonAgentInHardenedContainer` subtest's `--- PASS:` line), `observability` (with the step that requires the `--- PASS:` line of both gated tests), `real-model` and `demo-stack` (the script with the port checks, `TW_DEMO_PG_PORT`, the saved failure files and the cleanup). A job that passes does not run a step written to run only on failure, so those runs did not exercise the steps that print and upload the demo-stack failure files. The OpenAI and Anthropic adapters remain unverified over HTTP: their opt-in live tests have never run.
- A result recorded in a document is a result from one run on one machine, and the document names the machine.
