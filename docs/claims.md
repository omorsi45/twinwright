# Claims

Every claim the project makes, with the test or CI job that proves it and where that proof runs. The table has one row per numbered goal of the Twinwright Cloud design, one per bullet of its milestone sections and of its scope decisions, and one per factual claim in the README and the security notes.

How to read it.

- **Proven by** names backticked tests (for example `TestDemo`) and backticked CI jobs written as the workflow file, a slash and the job ID (for example `integration.yml/real-model`). A row that nothing proves says `not verified`. A row for scope that was dropped says `cut` and links the decision. No row is left without one of these.
- **Where it runs** is one of: local suite (`go test ./...`), CI fast lane (`ci.yml`), Integration (`integration.yml`), opt-in (the environment variable that enables it is named), or local run (the document that records it is named). `none` means nothing runs.
- A cited test is checked to exist and a cited job is checked to exist in its workflow file, by `TestClaimsTableReferencesExist`. Every relative link in the README, the architecture page, this page and the guide is checked by `TestDocLinksResolve`. Neither check says that a cited test is the right test for its claim, or that a cited job passed. Those are for the reader.
- The CI fast lane runs `go test ./...`, so every test marked local suite also runs there. A job in the Integration workflow runs on its triggers (a push to `main`, a pull request, or a manual dispatch); `perf` runs on manual dispatch only.
- A result recorded in a document is a result from one run on one machine, and the document names the machine.
