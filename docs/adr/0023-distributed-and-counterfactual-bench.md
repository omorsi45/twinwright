# ADR 0023: Distributed and counterfactual benchmark modes

- Status: accepted
- Date: 2026-09-29
- Supersedes: nothing. Extends ADR 0014 (Twinwright Bench).

## Context

Twinwright Bench measured agent behaviour in a single process. Every case seeded
a world, ran the agent inline, and judged the result. That covered reliability,
reasoning, safety, security, recovery and long-horizon behaviour.

It did not cover the two features the project leads with.

The distributed runtime (ADR 0020) has fenced ownership, crash recovery,
at-least-once delivery and idempotent effects, all exercised by unit tests in
`internal/worker`. None of it was visible to the benchmark. A reader could run
the suite, see sixteen green cases, and learn nothing about whether a worker
crash duplicates a refund. A benchmark that cannot see the headline feature is
not measuring the project.

Counterfactual analysis had the same gap from the other direction: the engine
existed and was tested, but no benchmark case ever asked it to explain a failure,
so the suite reported which cases failed without reporting why.

## Decision

A case declares a `mode`.

**`local`** is the default and is exactly the previous behaviour. Existing cases
did not change, and their reports are unchanged apart from two new summary
fields.

**`distributed`** executes the case through the worker runtime and kills the
first worker at the model turn named by `crash_at`. The case then reports, from
the store rather than from prose:

| Field | What it proves |
| --- | --- |
| `worker_crashed` | A crash was actually injected. |
| `crashed_fence`, `recovery_fence` | The second owner's token strictly exceeds the dead owner's. |
| `takeover` | The runtime classified the second claim as displacing a holder, not as a first claim. |
| `deliveries` | The run was handed out more than once, which is at-least-once delivery doing what it says. |
| `fencing_rejections` | A stale commit was refused after the run moved on. |
| `replay_verified` | The recovered ledger still reproduces. |

Alongside those, the case still reports `duplicate_refunds`, which is the point
of the whole exercise: two deliveries, one refund.

**`counterfactual`** runs the case locally and then applies an intervention set
to explain its failure. It reports the parent's failed checks, how many
interventions were evaluated, and whether one of them corrected the outcome.

## Why a crash at a named model turn

Cancelling the context on the Nth provider call leaves the ledger exactly as a
killed process would: the model request for turn N is persisted, everything
before it is committed, and the failure is never recorded because the process
that would have recorded it is gone.

The alternative was killing a real subprocess. That was rejected. It would make
the suite depend on process supervision and signal timing, and the crash point
would be wherever the signal landed rather than a boundary the case names. A
benchmark that cannot say which boundary it tested cannot compare two runs.

The shipped suite crashes at three different turns rather than one, because the
boundaries are not equivalent: before any tool call commits, after a read, and
after the refund is committed. The third is the one that matters, since that
delivery must not produce a second refund.

## Why time is controlled rather than slept

A takeover requires a lease to lapse. The default TTL is 30 seconds, so a
suite that waited would add half a minute per distributed case and its result
would depend on scheduling.

Distributed cases therefore drive a deterministic clock. The lease expires
because the clock advanced, not because the benchmark waited, which keeps the
suite fast and its results reproducible.

## Why a mode-incompatible field is an error

`crash_at` on a local case is refused, not ignored. So is `interventions`
without counterfactual mode, and counterfactual mode without an intervention
file.

A silently dropped `crash_at` is the worst available outcome: the suite would
report a green case in the distributed category that executed entirely in
process. The same reasoning makes a crash point past the end of the fixture an
error rather than a pass. A case that injected no crash and then reported a
successful recovery would be a false claim generated by the benchmark itself.

## Why the counterfactual parent must fail

`counterfactual.Prepare` already refuses a run that passes its judge, because an
analysis of a passing run has nothing to explain. That constraint is load-bearing
for the benchmark rather than inconvenient: it means a counterfactual case cannot
quietly become a second copy of a passing case.

It also constrains which cases can exist. The parent has to complete and fail,
which rules out a fixture that hard-stops on an error status. The shipped case
uses the unsafe ambiguous-commit fixture: it completes, double-refunds, and fails
three assertions, and the analysis reports that delivering the lost refund
response would have corrected the outcome.

## Consequences

The suite is 20 cases rather than 16, and the report carries an explanation rate
plus three distributed counts. `distributed` and `counterfactual` blocks are
pointers, so a local case omits them entirely: a zeroed block showing
`replay_verified: false` on a case that never replayed anything would read as a
failure.

The distributed cases share the billing world with the local ones, so a change to
that fixture moves both. That is accepted: the alternative is a fixture that
exists only for distributed cases, which would let the two paths drift until they
were no longer testing the same agent behaviour.

Nothing here runs against PostgreSQL yet. The cases open a SQLite store per case,
as every other case does. The distributed properties under test (fencing,
takeover, idempotent effects) are dialect-independent in the runtime, and the
dialect differences are covered by the PostgreSQL integration tests instead.
Running the suite against PostgreSQL is a later change, not a claim this ADR
makes.
